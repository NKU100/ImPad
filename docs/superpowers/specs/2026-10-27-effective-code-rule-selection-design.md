# 三应用有效代码与规则选择重构设计

状态：用户已确认语义选择方向及低维护的启动快照边界；分阶段实施中。版本号仅作提示，依据实际代码结构选择；多个不同完整方案冲突时拒绝安装。具体实施按分阶段计划推进。

## 目标与背景

用户要求降低热更新适配的长期维护成本，允许重构当前方案。目标是让微信、QQ、企业微信共享代码输入、规则评估、缓存和安装流程，新增热补丁不再默认引入一份按应用名或补丁状态分流的规则目录。

本次故障暴露了三个独立问题：原 APK 与活动代码不一致；缓存未绑定补丁；底层判断新增上层缓存包装后，旧 Hook 位置可能被绕过。已经完成的临时修复可以作为回归对照，但不能成为每个应用各自扩展一套选择器的起点。

当前 1.1.2 候选保留作对照，不因本设计自动提交、推送或发布。设计实施产生的新源码和 APK 必须重新验证。

## 方案比较与建议

| 方案 | 收益 | 代价与局限 | 建议 |
| --- | --- | --- | --- |
| 保留版本硬路由，增加通用补丁输入和失败后重查 | 改动较小，容易保留旧报告格式 | 同一版本内的多种代码形态仍需版本外的例外；错误规则未必能触发安全回退 | 不作为目标架构 |
| 统一有效代码视图，按完整语义方案选择 | 补丁只改变输入；规则与框架类型解耦；三个应用共用选择与恢复机制 | 需要迁移选择结果、缓存、回归比较和报告协议 | 推荐方案，本文按此展开 |
| 每个版本或补丁分别维护规则及优先级 | 单次适配容易定位 | 规则组合、优先级和补丁目录持续膨胀，难以解释为何选中 | 不采用 |

推荐方案中，版本号是诊断信息和查询顺序提示，不能排除其他有效识别器。最终结果必须由活动代码中的完整证据决定。当前每个应用的识别器集合有界，不遍历所有历史版本，也不下载历史 APK 来挑选运行规则。

## 范围与边界

保留 Kotlin、DexKit、dexlib2、libxposed，以及现有签名、包名、ABI 和安装包分包校验。继续使用三个应用入口和同一套 CI，不并行保留新旧运行模式。

本次不实现远程下发规则、不默认屏蔽 Tinker、不自动下载补丁，不新建规则 DSL 或完整字节码执行器。规则仍是普通 Kotlin 代码，复用有界的控制流与调用关系分析。

不承诺支持任意加固容器、任意内存加载器或任意进程运行中的代码替换。无法证明输入完整性及类解析顺序时，返回明确的不支持状态，不静默退回原 APK。

## 总体流程

```text
已验证的安装包身份 + 应用适配层发布的就绪上下文
    → 捕获活动代码快照与加载器拓扑
    → 构建与类加载顺序一致的有效代码视图
    → 评估该应用全部相关识别器
    → 形成完整 Hook 方案并合并严格等价结果
    → 唯一方案校验与运行时方法绑定
    → 一致性检查、批量注册、整体启用
```

静态 checker 从已验签 APK/split 构建静态代码视图；Android 从活动加载器构建运行时代码视图。两者使用同一个识别器集合、选择器与方案模型，区别仅在输入提供方式及能否绑定真实 Method。

## 一、应用适配层与代码输入

`AppAdapter` 只表达目标进程、业务代码何时可用、行为合同和安装策略。微信与企微继续在 Tinker 初始化返回后发布就绪信息；QQ 继续在其 QFix attach 返回后发布。不得因接口统一，改成所有应用都在同一个 Android 回调执行。

就绪信息 `ReadyRuntime` 包含包名、进程、Context、活动 ClassLoader 和本进程的就绪代次。它不提供“选择 002/003”之类的指令。

共享 `CodeSnapshotProvider` 注册表按加载器及输入能力工作，而非按微信、QQ、企微的包名分支。应用仍由 `AppAdapterRegistry` 按包名分发；这一必要的应用分发与规则选择分开。

首批拟支持范围；每项均须先通过下述运行来源能力验证，列入清单不代表已经具备支持：

- 普通文件支持的 PathClassLoader、DexClassLoader、DelegateLastClassLoader，以及已安装 base/split。
- 已就绪加载器中可验证的 Tinker 合并 DEX 归档。输入来自实际加载路径，不从磁盘“最新补丁目录”推测。
- QQ 就绪后的文件支持加载器通过同一提供器收集，不额外建立 QQ 专用规则选择器。

纯内存、加密或无法读取的代码源只有在提供器能够导出稳定内容并证明解析顺序后才支持；首版无法满足者返回 `UNSUPPORTED_CODE_INPUT`。识别到此类输入不能等同于“没有补丁”。

安装包的官方签名校验与运行时代码来源记录分开。补丁合并 DEX 不具有普通安装包身份，不能伪装成官方 base APK 通过验签；来源证据应说明它属于目标应用已加载的代码。

## 二、有效代码视图

`CodeSnapshot` 至少记录：安装包身份及逐包内容哈希、相关加载器拓扑与委派类型、各加载器有序 DEX 输入、逐 DEX 内容哈希、提供器及解析协议版本。持久化快照不保存 Java 对象或进程内地址。

`EffectiveCodeView` 以“加载器命名空间 + 类定义”为解析单位，构建类定义归属索引。字符串、方法、字段、继承和调用关系查询都必须使用同一视图。

关键约束：

1. 根据真实的 parent-first / delegate-last 顺序选择类定义；不能把所有路径简单拼成集合。
2. 补丁覆盖一个类时，该类的旧方法整体失效。不能从新类查找不到的方法中，继续拼接原 APK 的同名类方法。
3. 跨 DEX 的方法引用不等于重复类定义。判断重复必须基于实际 class definitions。
4. 沿用当前逐 DEX 查询以避免 DexKit 合并重名定义的问题，并在汇总前按定义归属过滤。不能通过按 descriptor 去重掩盖无法证明的覆盖关系。
5. 只有加载器顺序明确时才能消除被遮蔽的定义；同优先级冲突或未知委派行为必须报输入错误。

Tinker 只是代码输入的一种来源。选择器不能检查文件名 `tinker_classN.apk`、`hasPatch` 或某个补丁哈希来决定业务规则。

文件输入采用稳定读取检查：捕获文件身份、读取并计算内容哈希，再核对文件状态；读中变化则丢弃该代快照。内容会被原地修改且无法稳定读取的输入，必须先物化为私有快照，或明确拒绝。不得仅凭路径、大小和修改时间宣称代码内容相同。

### 启动快照与绑定的证据边界

用户在能力验证后确认首版采用低维护的启动快照保证。快照证明的是就绪时观察到的文件支持 DEX 内容、加载器委派及有序输入；不宣称证明实际已定义 Class/Method 的 ART DEX 来源，不新增通用 ART 内存解析器。

现有锁定 DexKit 的 ClassLoader 桥不会自动处理完整父链；反射 Method 查询实质上按 descriptor 查询；合并重名类不提供正确覆盖语义；导出函数还会覆盖等长 DEX。首版不使用这些接口认证来源。文件支持输入逐源稳定复制、逐 DEX 分离，以 dexlib2 的 class definitions 构建归属索引，再对每个 DEX 分别调用现有查询接口。

首版依赖应用原有的启动就绪时机，支持已验证的普通文件加载器布局和委派类型。绑定检查实际声明类加载器是否对应快照中预计的加载器、方法签名及形态；它能发现加载器层面的不一致，不能区分同一加载器中已驻留的旧同名类。对已观察到的布局或输入变化丢弃计划；无法发现的先加载后注入、同一加载器内任意改码不在保证范围，不把这些情况报告成已经认证。

不支持的加载器、无法读取或无法稳定复制的输入，返回 `UNSUPPORTED_CODE_INPUT` 或代码变化状态，不静默退回 base。报告区分 `STARTUP_FILE_SNAPSHOT` 与严格来源证明；本次能力验证保留为设计取舍证据，不将原来的 `UNSUPPORTED` 报告改写成通过。

扫描索引在同一快照内共享。暂不改写 DexKit 引擎；具体内存/临时文件存储方式留给实施者根据锁定 API 和实际内存开销选择，但必须满足相同的稳定快照合同。

## 三、规则表示与完整方案选择

规则按业务能力组织，例如微信平板登录、QQ 设备类型、企微本地平板判断。规则识别器可以支持多个已测试的编译形态，形态变化不自动升级为新的业务策略。

识别器输出完整关系图及方案，不先对 tablet、login 等独立方法计数后立即判定整条规则多解。例如找到两个平板判断候选、但只有一个能与登录入口构成完整有效关系时，可以得到一个完整方案；判断标准是完整方案的数量。

识别器结果分为：

| 结果 | 含义 | 对选择的影响 |
| --- | --- | --- |
| `NoMatch` | 已完整评估，没有完整方案，可附带部分匹配诊断 | 继续评估其他识别器 |
| `Plans` | 已完整枚举，一个或多个完整方案 | 汇总后做等价及唯一性检查 |
| `Incomplete` | 超时、取消、分析预算耗尽或必需关系无法判定 | 返回 `ANALYSIS_INCOMPLETE`，停止安装 |
| `UnsupportedInput` | 必需代码或加载器语义无法分析 | 停止安装 |
| `EvaluationError` | 解析器异常、合同损坏等真正错误 | 停止安装，不能被另一条成功结果掩盖 |

“部分目标找到、另一些没找到”属于有诊断的 `NoMatch`，不是自动当成解析器错误；也不能因为它缺少必要目标就安装部分 Hook。损坏的输入、非法指令解析及识别器抛出的异常仍属于错误，不能降级为未匹配。

评估范围为当前应用、当前行为合同下的全部已注册识别器。版本提示可以改变执行顺序、共享查询的预热次序，不能在第一个成功结果后短路，也不能阻止发现冲突。

每个识别器必须区分“完整搜索后没有更多结果”与“搜索被截断”。候选上限、调用图深度、循环处理或时间预算不能把剩余未知候选裁掉后返回 `NoMatch`/`Plans`。即使已发现一个完整方案，只要任一必需识别器未完成，也不能选择它；已经证明两个不同完整方案时可直接返回冲突，因为继续搜索无法恢复唯一性。报告记录完成状态、截断原因和已发现方案数。

完整方案的执行身份由以下内容共同决定：行为合同版本、安装策略及回调语义版本、有序 Hook 角色、目标 descriptor/shape/有效定义归属、Hook 阶段、返回值或参数等策略配置。

只有执行身份严格相同的方案才能合并为一个结果，并保留全部识别证据。仅仅使用同一策略、返回相同布尔值或拥有相同方法签名，不构成等价；Hook 不同层的方法也不构成等价。

零个完整方案返回 `NO_MATCH`；一个不同的完整方案返回 `SELECTED`；多个不同方案返回 `PLAN_CONFLICT`。不得以规则编号、应用版本、补丁状态、匹配数量得分或识别器执行顺序打破冲突。

## 四、微信 001/002/003 的收敛

这三条路径首先按同一行为合同重新组织为微信平板登录识别器族，支持已有内联机型判断、聚合判断、缓存重读和缓存包装等有证据的形态。不同形态是识别证据，不再分别建立“普通 catalog / Tinker catalog”。

此次确认的共同目标是能支配调用路径的上层平板判断入口，以及与它关联的登录入口。识别器需要证明上层入口对底层结果的转发；存在缓存时，还需证明缓存返回路径和加锁计算路径的关系。直接包装和缓存包装归一化到同一 Hook 角色。

不得将原 002 的底层 Hook 与 003 的上层 Hook 仅按“效果差不多”合并。迁移后的统一方案必须明确选择上层目标，并重新验证聊天页行为约束、原方法执行语义、登录按钮和扫码页面。

如果 8.0.69 等固定基准无法证明同一上层策略成立，应保留一个具有不同结构前提的识别形态/策略并独立验收，不能以保留旧版本支持为理由取消关系校验。不同方案同时成立时仍视为冲突。

原 001/002/003 的来源、历史测试和发布记录保留用于审计；新运行路径不同时运行新旧两套选择器。是否能归为同一安装策略由真实固定样本验证决定，不先假设已经完成。

QQ 与企微迁移到相同的方案及证据模型。它们原有的 TABLET 枚举和三个本地判断目标等业务约束继续保留；不为接口整齐而削弱各自的完整性要求。

## 五、缓存、绑定与恢复

新的持久化缓存协议与旧协议隔离，只保存成功解析的完整方案及证据，不保存 Method、ClassLoader 对象或未匹配结果。

缓存键覆盖：安装包身份、全部 APK/split 内容、有序有效 DEX 内容及加载器解析模型、完整识别器目录与实现指纹、策略实现、提供器/解析器版本、DexKit 锁定身份和缓存协议版本。新加入一个可能产生冲突的识别器也必须使旧缓存失效，不能仅比较上次选中的规则。

持久化缓存不以进程内 loader 地址或安装目录绝对路径作为唯一身份。同样内容移动位置不等于新的业务形态；本进程绑定时仍必须重新核对实际加载器及来源。

命中缓存后，先在当前就绪上下文中绑定全部目标，再安装。绑定必须校验方法签名、静态性和快照模型预计的声明类加载器；仅在父链上不足以通过这一检查。它不提供同一加载器内已驻留方法的 ART 来源证明。

失败处理是共享状态机：

1. 缓存方案绑定失败：删除该精确键的缓存；对当前稳定快照完整重查一次。
2. 重新解析后的新方案仍绑定失败：返回 `RUNTIME_BINDING_MISMATCH`，停止，不继续试探其他 Hook 位置。
3. 捕获、解析或安装前后发现输入代次变化：丢弃方案及未生效注册，最多重新捕获一次；再次变化返回 `CODE_CHANGED_REPEATEDLY`。
4. 真实解析异常、计划冲突和注册失败不触发“换规则直到成功”。

每个就绪事件最多两次解析尝试；缓存重查与代码变化共享这个预算，不能分别嵌套重试而产生四次或更多扫描。达到上限时明确报出最后失败原因和已执行尝试数。

## 六、安装一致性与运行生命周期

通用安装器先绑定全部目标、准备全部 HookSpec，检查快照代次，然后注册。各回调在整个批次就绪前保持透传；注册完成后再次校验快照，才整体启用业务回调。

任何失败均先关闭批次业务回调，再逆序撤销已注册 Hook。撤销失败必须报告 `ROLLBACK_FAILED` 并要求目标进程重启，不得声称回滚成功。该机制提供可验证的一致性检查与回滚，不宣称跨整个应用进程的绝对原子性。

首版以启动就绪后的代码代次为工作范围。提供器或就绪桥明确观察到后续代码代次变化时，停止旧批次业务回调并报告 `RESTART_REQUIRED`；不自动杀死用户应用，不尝试在业务运行中反复卸载、换规则和重新挂接。未被观察到的任意运行中改码不属于首版保证。

## 七、静态检查、运行报告与历史验收迁移

当前 `static_regression.py` 会把新 checker 的 ruleId、strategyId、targets 与历史记录精确比较。通用重构可能有意改变 Hook 目标，因此不能只修改运行时而保留旧比较，也不能将比较削弱为“任意 SELECTED 即通过”。

本次采用显式、版本化迁移：

- 历史 acceptance 和原始证据原字节保留，继续绑定当年的模块、源码和计划，不覆盖为新结果。
- 新建重构迁移清单，明确每个既有固定代表的原记录引用、安装包身份、预期行为合同，以及允许迁移的目标/策略变化。它只用于回归与审计，不参与运行准入。
- 新报告记录代码快照身份、行为合同、完整方案执行身份、全部识别证据、绑定和安装结果；不同完整方案不能因历史记录允许变更就被选择器接受。
- 每个固定代表仍须静态唯一，并用同一份新正式签名 release/R8 APK 通过独立无账号运行验收，之后才能登记新模块结果。无法完成者是迁移阻塞，不删除样本来使回归变绿。
- 移交完成后，日常回归比较新登记的固定期望。缺少、损坏或未经独立验收的迁移登记必须失败关闭，不自动首次迁移或重建 acceptance。

### 首次迁移的引导流程

现有流水线先比较历史固定计划，再运行应用；新计划登记又要求运行验收。首次切换不能要求先有新登记，也不能复用“无历史样本”的首次登记豁免。

采用一次性、显式授权的迁移验证入口：冻结旧 acceptance、固定样本列表与迁移清单，在独立 checkout 用新 checker 对清单中全部原始样本进行身份检查、完整枚举和唯一性验证；经独立核对后，冻结逐样本新预期方案及报告哈希。迁移入口以这份冻结预期作计划比较，仍保留完整样本覆盖、身份、静态验证和运行验收门禁。普通日常入口在此期间继续使用旧基线，不接受迁移参数来跳过失败。

随后以同一份最终 release APK 运行三个应用的独立验收；阶段证据写入迁移证据包，不提前写正式 acceptance。控制器校验全部样本和运行结果后，才登记新结果并原子切换活动基线。迁移清单缺项、样本替换、源码或 APK 变化、证据不完整均禁止切换。旧记录保留；失败可以从原基线继续工作。切换后删除一次性入口，常规适配流程不能自行启用它。具体实施计划必须同时覆盖 workflow 的前置静态门禁和登记器，不能只修改其中一端。

### 补丁输入的独立预期

`ExpectedPlanArtifact` 绑定精确代码快照、规范化加载拓扑、行为合同、执行身份、角色及快照中的定义归属。它由独立 checker 在本次模块运行前产生并冻结；首次迁移的目标变化还须独立审查。运行模块上报的 `SELECTED`、目标列表或缓存不能成为自身的期望值。

无补丁时，已验签 APK/split 的预期仅适用于同一代码快照。补丁运行必须从可重放的精确补丁及加载配置独立生成预期，并核对启动快照、声明类加载器绑定、模块身份与业务页面；报告保持启动快照保证的边界。不能拿 base 的目标与补丁目标直接比较，也不能因两者可能不同就忽略目标比较。

区分“解析样本”和“可运行补丁样本”：前者可以只是合并 DEX；后者还需具备应用实际接收并加载该补丁所需的原始包、校验元数据及相关资源/原生库（如适用），并记录来源和哈希。本次只有已提取的合并 DEX，可作为真实解析/Android 探针样本，尚不能当作完整 Tinker 重放包。不得为填补该缺口操作用户手机。

无法在独立环境重放精确补丁时报告 `PATCH_REPLAY_UNAVAILABLE`，不能登记该补丁的完整运行支持。实施前冻结必验矩阵：三个应用既有固定代表不能减项；若本次发布宣称解决该补丁下的完整运行问题，该补丁的独立运行验收也必须通过。代码探针的通过可以单独报告，不能替代这一门禁。

checker、候选准备、源码指纹、raw 日志解析、production verifier、登记器、三个应用 workflow 和适配提示词共同升级报告协议。正式路径只使用新协议；历史协议读取器仅用于原证据审计，不作为运行时回退开关。

已有独立 checkout、模型上下文可见性与写入权限边界保留。自动适配可以在限定范围增加应用识别器/样本，但不能通过修改代码输入信任边界、选择器、验收器或历史登记来制造通过。

## 八、验证矩阵与完成条件

| 层次 | 必须验证的情况 |
| --- | --- |
| 输入与覆盖 | base/split、Tinker 合并归档、父优先和子优先、类整体遮蔽、同名不同定义、旧方法不复活、读中变化、缺失文件、未知加载器 |
| 选择器 | 单一完整方案、部分匹配但无方案、两个不同方案冲突、严格相同方案合并、枚举截断不能选中、错误不被成功覆盖、版本提示变化不改变最终选择 |
| 缓存 | 同路径换内容、补丁增删、定义顺序变化、识别器增加、策略变化、缓存绑定失败后一次重查、共享重试预算 |
| 安装 | 部分注册失败、注册中代次变化、批次未就绪透传、逆序撤销、撤销失败、重启后重新绑定 |
| 微信语义 | 8.0.69、官方 8.0.79、Play 3182、本次补丁代码；直接包装、缓存包装、错误转发、错误字段和错误登录控制关系 |
| 三应用运行 | 微信入口与稳定扫码页面；QQ 既有手机/平板 AppID 和采集完整性合同；企微入口及扫码页面；全部绑定同一份最终 release/R8 APK |

真实 DEX fixture 是规则解析回归；Android 补丁代码探针是原生解析与反射验证；两者不能冒充完整安装补丁后的应用运行验收。后者必须有实际补丁加载及来源、关闭/启用对照和业务页面证据。

不使用真实账号、不扫码、不提交登录，不宣称服务端登录或双设备共存已验证。不再操作用户正在使用的手机；使用独立 AVD 或经另行授权的独占运行环境。

性能基线在实施前冻结：首次解析耗时、缓存命中耗时、DEX 读取/索引次数、峰值内存。识别器共用快照和索引，缓存命中不全量扫描；不得在看到退化后放宽基线来宣称达标。具体阈值由实现前测量决定并写入实施计划。

完成条件是：三个 App 走同一套新流程；没有按包名或补丁状态决定规则编号的核心分支；所有固定代表均保留且完成迁移验证；新源码、模块身份和证据一致；旧运行模式、临时 Tinker catalog 和重复缓存/安装通道已删除。

## 九、重构边界与建议顺序

| 位置 | 变更职责 |
| --- | --- |
| `compat-core/.../rules` | 新的完整方案、证据、等价及冲突模型；版本区间不再承担硬选择 |
| `compat-rules/RuleSession.kt` 及规则实现 | 有效定义归属、一致的查询视图、语义识别器和编译形态归一化 |
| `app/.../runtime` | 输入提供器、快照、缓存协议、运行时绑定、共享恢复与批量安装 |
| 三个 `AppAdapter` 与 `ImPadModule` | 保留进程/就绪/策略差异，删除微信专用 catalog 分流 |
| `compat-checker`、`scripts/ci`、workflow | 同一解析器的新报告、迁移清单、严格原始证据验收和登记 |
| 文档、测试、构建指纹 | 新维护边界、真实 fixture、全部新模块源码的身份覆盖 |

建议按四个可验证阶段推进：先完成活动来源 API 能力验证（已完成，用户确认采用启动快照边界）、冻结支持矩阵、基准与报告迁移合同；再实现快照/有效视图；随后统一语义方案、缓存和安装；最后切换 checker/CI、完成三应用独立验收并删除旧运行路径。中间可以在测试中对照新旧结果，但正式模块不保留用户可切换的双模式。

这是中等偏大的架构整理。最主要的投入在类定义覆盖语义、完整方案冲突模型和历史验收迁移，不是新增三个应用各自的补丁识别文件。无需更换整个 Hook 框架或重新实现 DexKit。

## 已确认的设计决策

用户已确认取消版本硬路由、采用完整方案唯一性和统一有效代码视图。版本提示不得排除识别器；多个不同完整方案冲突时拒绝安装。能力验证已确认现有 API 不支持严格逐方法来源证明；用户进一步确认首版收窄为启动时稳定文件快照与显式加载顺序，不承诺任意运行中注入或改码来源认证。

接口的最终 Kotlin 命名、索引存储、现有文件的拆分粒度、基线采集脚本由实施者决定；上述信任、选择、覆盖、失败及迁移合同不属于可随意调整的实现细节。
