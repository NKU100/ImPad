# ImPad 运行时特征匹配迁移设计

状态：设计草稿，已处理独立检查提出的区间边界问题，待用户确认。本文定义目标与约束，不是实现完成报告。

## 目标与范围

将逐 APK SHA、预期描述符的运行时准入，迁移为可信应用身份校验、versionCode 路由、DexKit 特征匹配和明确的 Hook 策略。测试和真机执行同一份路由、查询、完整性检查及选择逻辑。

先建立公共框架并迁移 QQ，再接入企微证明多 Hook 和不同回调策略能复用该框架。微信在过渡期保留现有路径；微信完成独立规则分析、移植和验收后，才移除剩余旧运行路径。本次实施计划必须明确 QQ、企微交付边界，不把未验证的微信迁移算作完成。

所有应用共用框架，只声明各自的包名、可信签名、支持 ABI、进程要求、规则和策略。应用差异不进入公共解析器的版本分支。用户开关、稳定签名与发布行为需保持。历史支持的迁移按下述最旧版本基准执行，不要求本轮逐项迁移全部已支持 APK。

DexSQL 只用于分析。模块和真实 APK 回归均执行 Kotlin 中的 DexKit 查询，不建立 SQL 转换层、统一查询语言或第二套测试匹配器。规则随模块发布，本轮不引入远程规则更新。

## 改造主线与收敛约束

自动发现、指定 URL 和适配产物都是候选来源，不能各自维护验证流程。独立验证与适配共用以下主线：

```text
自动发现 / 指定官方 URL / 已有候选产物
                  ↓
         统一候选准备与身份核验
                  ↓
        共用验证：静态检查与回归
                  ↓
           独立运行验收
                  ↓
            统一结果与证据
             ↙          ↘
       只验证：返回结果   外层控制器：登记 / 待审 PR

需要适配：由上述验证失败及诊断进入隔离分析
          → 新增规则 / 策略 / 暂定路由 → 构建候选模块
          → 回到同一验证入口
```

独立验证只验证指定输入并输出结果，不启动模型改代码；适配控制器可以在规则或行为不兼容时进入分析，但不得因环境 unavailable 自动修改规则。两者的区别在于外层是否允许产生代码提案，不在于使用不同的验收断言。

共用验证的输入至少包括显式 app_id、候选 APK/split 的原字节与真实身份、待测模块的原字节与哈希、规则及路由对应的源码身份，以及本轮适用的回归登记快照。URL 只负责获取 APK，不充当身份依据。需要构建模块时在进入运行验收前完成；验证期间不修改 APK、模块、规则或登记表。报告同时保留静态、回归、运行各阶段状态及证据，外层不得把未执行阶段当作成功。

复用现有 workflow 和脚本进行职责收敛，不新增通用任务引擎、插件调度框架或与旧系统并列的验证实现。新共享代码必须消除实际重复或隔离明确的平台依赖。

| 处理 | 现有部分 | 改造后的职责 |
|---|---|---|
| 保留 | compat-checker、runtime-validation.yml、AppSmoke、ReDroid 环境及各应用验收断言 | 继续承担静态与运行验证，内部接入共享规则 |
| 保留 | bootstrap、HookInstaller、下载与身份核验、checkpoint/resume、可信控制器 | 沿用已有能力，按新输入及结果接口调整 |
| 合并 | 官网发现、手动选择、适配产物各自的候选准备 | 同一候选输入约定及准备逻辑，来源只决定怎样取得输入 |
| 合并 | 适配迭代与独立验证的验证编排及证据判定 | 共用检查、行为断言与结果判定；设备生命周期可由不同调用方管理 |
| 分离 | runtime_task 的证据判定与 PR/登记写入 | 纯验证返回结果，外层控制器决定是否登记及发布提案 |
| 删除 | 已迁移应用按 APK SHA / expectedDescriptor 准入的运行路径与旧 assets | 每应用切换验收完成后删除对应路径，不保留新路径失败后回退旧路径 |
| 删除 | PR 存在才允许验收、隐式微信默认、重复候选及结果分支 | 验证由明确输入驱动，发布按验证结果执行 |
| 暂留 | 尚未迁移微信的旧解析、assets 和测试 | 显式 legacy 路径；微信独立迁移验收完成后删除 |
| 暂缓 | 热补丁适配、补丁阻断、远程规则更新 | 不进入本轮实现或交付门槛 |

## 已确认的选择原则

1. 用 `versionCode: Long` 路由，`versionName` 只用于展示。
2. 签名是应用身份校验条件，不是规则分组维度。当前不按渠道或所谓代码族分组。
3. 历史规则保留固定区间，最新规则开放上界。规则内容和回调语义按不可变 ID 保留；需要变化时新增 ID，不修改已有实现，不引入规则 revision。
4. 版本空档由手机运行时尝试左右相邻规则；不组合两侧的部分 Hook。
5. 流水线主要获取新版，先验证现有规则；需要新策略时才增加规则和区间。官网回退构建仍按现有区间与空档逻辑选择，并由运行验收确认；需要新规则但不满足向前建区间条件时停止自动修改路由，转人工分析。
6. 每个应用常规回归最多三个 APK：最近三条规则，每条选择首次适配并完成验收的一个 APK。本轮候选另行检查。
7. 保留 APK 验收登记表，作为回归输入和预期断言来源；手机不读取它作为准入清单。

## 当前实现与可行性证据

当前 `RuntimeCompatibilityResolver` 先按基础 APK SHA 寻找 `CompatibilityTarget`，再要求结果等于登记的 `expectedDescriptor`。`ImPadModule` 从模块 assets 读取 `targets.json`。`InstalledBuildIdentityReader` 当前将版本号填为 0、签名填为空，旧解析器从目标补足身份；新路径必须读取真实安装信息。

现有 QQ adapter 等待 QFix attach，企微和微信 adapter 等待 Tinker。当前先解析基础 APK，再等实际 ClassLoader 安装 Hook。新路径在装载器准备好后执行解析并安装 Hook；本轮先验证原始 APK 与必要 split 的代码输入，不据此承诺能分析热补丁后的实际代码。

桌面可行性试验使用 DexKit 官方提交 `f86a036ef2f000e3b42a2e52a25ae3f27770e7f0` 的 CI artifact。同一 Kotlin 规则分别以 JVM JAR、Android AAR API 编译，并在 macOS arm64 JVM 上运行：QQ 9.3.70、9.3.75 各唯一匹配；企微负样本零匹配；字段、字符串、调用关系和目标与之前离线结果一致。

试验只证明桌面 JNI 与共享 API 路径；Linux JNI、Android native 加载、实际 ClassLoader、Hook 时序和行为尚未验收。试验材料在 `work/dexkit-jvm-spike-20261019/`，属于本地研究资料，不是模块依赖安装方案。实现前需确定可长期获取、固定提交和哈希的 JVM、Android、native 产物；不能依赖会过期的 CI artifact。

## 已知缺口：热补丁适配

本轮暂不处理热补丁适配，也不阻止测试环境或用户运行时的热补丁加载。不实现补丁获取、增量还原、完整探测、专用规则路由或补丁状态的自动验收。

当前 versionCode 区间只负责选择原始 APK 的候选规则，无法区分同 versionCode 的不同补丁状态。现有规则可能继续适用于未影响目标的补丁，但这不构成补丁已适配的结论；唯一匹配和方法签名校验也不能证明补丁未改变业务语义或调用路径。

本轮登记与验收结论限定于已记录的 APK 输入和实际测试状态，不推广为该版本所有热补丁均兼容。若测试中观察到补丁状态，应保留相关证据并注明，不能当作无补丁基准；未观察到补丁也不等于已证明补丁不存在。完整补丁识别不是本轮交付要求。

后续处理此缺口时，需要分别验证 Tinker、QFix 的有效代码获取或还原、基础 APK 与补丁组合身份、同版本规则选择、缓存隔离以及独立运行验收。以下有效代码与缓存约束以本轮可验证的 APK/split 输入为范围，不要求本轮补齐热补丁支持。

## 代码组织

以下模块边界是本设计的建议，类名可在实施计划中调整，职责必须保留。

| 位置 | 职责 | 平台限制 |
|---|---|---|
| `compat-core` | 应用身份模型、区间、规则引用、解析结果、选择算法、缓存键 | 不依赖 Android 或 native 加载 |
| 新 JVM 模块 `compat-rules` | 各应用 Kotlin 规则对象、DexKit 查询及后过滤、完整规则解析流程 | 编译依赖 DexKit API，无 Android Context/ClassLoader 获取逻辑 |
| `compat-checker` | 获取本地 APK 身份，加载桌面 native，调用共享解析流程，输出检查报告 | JVM 宿主边界 |
| `app/runtime` | 真实包身份、有效代码输入、缓存存储、实际 Method 校验和安装流程 | Android/libxposed 边界 |
| `app/apps/<app>` | 进程和 bootstrap、回调策略实现 | 应用行为边界 |
| `scripts/ci` | 发现、候选调度、登记表、回归选择、独立验收和发布控制 | 不实现特征匹配 |

`compat-rules` 用 Kotlin 对象直接编写 DexKit matcher 与必要后过滤，允许普通 Kotlin 查询函数。无需限制成可翻译的 DSL。规则不调用宿主反射来决定静态候选；实际反射验证在 Android 边界完成。

DexKit API 与 native 版本必须一致。共享模块仅编译依赖 API；checker 提供 JVM 实现和桌面 native，app 提供 Android AAR 和 Android native。Gradle 必须避免同一 API 的 JAR 与 AAR 重复进入 APK。跨平台使用相同源提交，报告记录具体产物哈希。

公共核心的数据至少包含：

```text
RuleId                     唯一标识一份不变的查询及策略绑定声明
StrategyId                 一份不变的回调语义
VersionBinding             ruleId + inclusive min + inclusive max（最新为无上界）
RuleDefinition             id + required targets + strategyId
ResolvedPlan               ruleId + strategyId + targetId→descriptor
RuleResolution             Missing / Unique(plan) / Ambiguous / Error
SelectionOutcome           Selected / NoMatch / Ambiguous / RuleConflict / Error
```

描述符、版本区间和应用常量只存在于应用声明、分析结果或登记表中。公共解析器不得包含 `if (app == qq)`、具体版本号或业务方法名。平台和状态分支集中在相应边界与通用决策器。

### 规则与策略

`Rule` 是一套定位完整 Hook 集合的查询及其策略绑定，`RuleId` 唯一标识该不可变实现。不设 revision；需要改变查询条件或策略绑定时新增 ruleId，原规则及其验收记录保留。规则 ID 不是应用版本号，一条规则可以覆盖多个 APK 版本。

一条规则负责一个完整 Hook 集合。各目标分别唯一匹配后，才能产生 `Unique(plan)`。候选计数按实际定义计算，不能按描述符去重来隐藏多个定义。引用、调用者 DEX 局部索引、字段与实际定义需正确区分。

回调由策略 ID 明确指定。企微的 local 常量策略与 service/proceed 策略分开声明；安装器不再按 `getDeviceType` 名称和参数形状猜策略。若查询需要因混淆名称变化而调整，新增规则 ID；返回值含义、执行前后或 proceed 行为改变时，新增策略 ID，并新增绑定该策略的规则 ID。已有查询仍能匹配时无需新增规则。

已有规则的查询、必需目标集合、策略绑定及已有策略实现均不修改；需要变化时新增对应 ID，并保留旧实现。收缩适用区间允许修改路由声明，但必须经过回归。规则的添加顺序不能决定匹配优先级。

不可变范围包括规则或策略依赖的专用辅助函数、常量和配置，不能通过修改这些依赖间接改变已有 ID 的行为。新规则可以复用行为保持不变的依赖；需要改变专用依赖语义时新增实现并由新 ID 引用，旧 ID 继续引用原实现。公共解析器与通用基础设施允许修正，但必须执行适用的有界回归和受影响的确定性单测；若预期选择或业务行为发生变化，仍遵守新的独立验收要求，不能把它伪装成旧规则原有行为。

## 版本路由与空档

区间使用包含端点的范围，必须有序、不重叠，`min > 0`，最多最后一条无上界。每个应用的规则创建顺序独立保存，不把区间排序或发现时间当作隐含匹配优先级。

| 安装版本位置 | 待尝试规则 |
|---|---|
| 位于已定义区间 | 该区间的一条规则 |
| 两个区间之间 | 左右紧邻的两条规则 |
| 高于已有验收版本，仍在最新开放区间 | 最新规则 |
| 小于最早下界 | 最早规则，作为未验收候选尝试；结果不等同于正式支持 |

在空档内，只有一条规则给出完整 `Unique`，其他规则均为 `Missing`，才选它。两条规则都唯一匹配时返回 `RuleConflict`，即使描述符相同，也不凭添加顺序或相同目标选择策略。任何一条出现多候选或解析错误，都停止自动选择。此处采用严格唯一规则，不引入等价策略合并或评分。

匹配成功允许手机尝试安装 Hook，但不能据此写入已验收状态。匹配缺失、歧义、冲突、身份不可信或方法无法加载时不安装业务 Hook。

最新规则的开放上界仍存在误匹配风险：唯一结果不能证明新版业务语义正确。流水线验收用于发现这一风险；收缩区间或新增策略需要随新模块发布，已安装的旧模块不会因登记表更新而自动改变行为。

### 流水线如何建立区间

规则首次通过独立验收的构建定义其初始下界。最新规则保持开放上界；成功沿用时只增加验收记录，不必为了未知新版生成模块改动。

自动追加区间只处理向前演进：A 必须是当前开放上界的最新规则，候选 C 的 versionCode 必须严格大于当前所有规则已验收构建的最高 versionCode。若 C 不能沿用 A，提出新规则 B。B 验收通过后，A 的上界封在 A 当时最高的已验收 versionCode，B 的下界设为 C 的 versionCode。不能直接把 A 上界设为 `C - 1`，否则会抹掉未采样版本的空档。

例如 A 起于 100，最后已验收为 180，B 起于 220，则形成 A `[100,180]`、B `[220,∞)`，181～219 在手机上尝试两侧。B 未通过验收时，不宣告新区间或新策略已可用；失败构建保留诊断与待处理任务。

官网回退、历史空档候选或同 versionCode 的另一构建若能沿用当前路由选出的规则，只新增验收记录，不改变区间、规则创建顺序或首次验收代表。若需要新规则、不同策略或扩大既有区间，且不满足上述向前条件，则保留候选、匹配诊断与失败或待验收状态，报告 `ROUTING_REVIEW_REQUIRED`，停止自动建区间及支持登记；不得套用向前封口算法，不得重划历史绑定或把候选强行交给最新规则。

这是本设计采用的保守默认：历史路由重划不在自动追加流程范围内，需另行提出具体区间与受影响样本的回归、运行验收方案，再交人工审阅。分析分支可以保留新规则提案，但不得把提案当作已生效路由，也不增加常规三个 APK 的回归上限。

同 versionCode 的不同 APK 不分渠道路由，仍各自按真实代码匹配。登记和验收以精确 APK 身份区分；若同区间规则无法处理其中一个构建，必须显式报告，不能靠版本名称掩盖。

## 测试与真机共用执行路径

共享流程是：应用身份校验 → 路由 → 执行候选规则 → 全目标完整性及唯一性检查 → 选择 → `ResolvedPlan`。checker 和 app 调用这一流程，不各自维护选择分支。

JVM 输入由已核验的基础 APK、必要 split 及明确的 DEX 集合组成。Android 本轮使用实际安装的基础 APK 与必要 split 作为查询输入，并在 bootstrap 后通过实际 ClassLoader 校验及获取 Method。输入准备可以不同，规则与决策相同；这不等于已读取热补丁代码，已知的输入差异应保留诊断。

Android 需要读取真实 `longVersionCode`、包名、ABI 和签名，签名缺失不得从规则或登记表填入。APK SHA 用于身份记录和缓存，不是未知版本的准入门槛。

QQ 保持 `:MSF` 进程范围，企微保持当前相关进程范围。现有 attach/Tinker 等待器可复用，但业务解析及 Method 校验应在装载器就绪后、相关自然登录请求前完成。native 加载和实例创建由公共 session 管理，同一次解析的相邻规则共用 session，使用完关闭。

本轮验证装载器就绪后的 APK/split 查询、Method 获取和安装时序。必需的 APK/split 输入不可读取时报告 `CODE_INPUT_UNAVAILABLE` 并停止业务 Hook；未知 bootstrap 结构需要适配，不能未经验证提前安装。patch 与内存 DEX 的完整读取另列后续工作，不作为本轮交付门槛，也不把基础 APK 查询或缓存命中报告为补丁代码已验证。

`ResolvedPlan` 在 Android 边界转换为实际 Method，检查实际类、参数、返回值、静态性和装载器归属，再绑定策略。整组 Method 与回调准备完毕后，复用 `HookInstaller` 批量注册和逆序回滚。不把局部安装成功报告为整组成功。

`ResolvedPlan` 只保存不可变的描述符、方法形状与策略标识，不持有依赖已关闭 bridge 的 DexKit 结果对象。所需元数据在 session 有效时完整提取；代码输入在解析至安装期间改变时，丢弃计划并重新解析，不能继续安装旧计划。

### 缓存

缓存至少绑定应用、可信签名、真实 versionCode、基础 APK 与全部参与查询的 split/DEX 的内容身份、规则 ID 与内容摘要、路由声明摘要、策略 ID 与内容摘要、解析器与 DexKit 版本。路径、文件长度和修改时间只能用于快速定位，不足以单独证明缓存有效。

代码或规则变更必须失效。命中后仍进行实际 Method 与策略验证。缓存只证明已记录的 APK/split 输入及规则的解析结果，不证明补丁状态兼容；已知代码输入发生变化时不得继续复用。补丁身份与缓存隔离的完整支持留待后续实现。缓存读写失败不改变匹配条件；可重新解析，无法解析则失败关闭。

## APK 验收登记表与回归

迁移应用采用独立的开发者登记表，例如 `compatibility/<app>/acceptance.json`。它保存构建事实、期望计划和验收证据，不包含可供模块执行的 matcher，不打包为运行时准入 assets。

每个登记项至少保存：

| 字段 | 用途 |
|---|---|
| recordId、应用、packageName、versionName/versionCode、ABI、signer、APK/split SHA | 精确构建身份 |
| 官方获取地址或显式本地 fixture 引用 | 可复跑输入，下载后校验内容哈希 |
| expected rule ID、strategy ID、各 target 的 descriptor/shape | 回归预期 |
| expected selection=unique、实际候选规则与采样路由模式 | 说明直接区间或空档选择 |
| module SHA、规则内容摘要、源提交、验收 contract/version、运行与证据定位 | 当次验收溯源 |
| 验收状态与时间、是否为规则首次成功记录 | 选择回归代表样本 |

预期计划只能在独立运行验收确认后登记。回归程序只读登记表，当前输出不能自动成为新的期望。正常回归比较目标规则、策略和方法；原验收 module SHA 是溯源字段，不要求当前待测模块等于历史模块。

新增规则或调整路由导致某个 APK 的预期选择或描述符改变时，需要新的独立验收记录并明确替代关系；不能覆盖旧规则、旧预期或旧证据。迁移已有 profile 时可以提取身份和获取地址，旧模块的运行结论不能直接证明新解析器、规则和策略已通过运行验收。

### 首批迁移基准

每个迁移应用只选原有已通过运行验收的最旧版本作为首批迁移基准，按真实 versionCode 的最小值确定；同版本存在多个构建时固定其中一个精确 APK 身份，不扩展为全部变体。当前登记中的基准为 QQ 9.3.1（14378）、企微 5.0.8（70675）；微信后续迁移时以 8.0.69（3040）为基准，本轮仍走 legacy 路径。

基准需在新解析器、规则与策略上完成独立静态及运行验收，不能继承旧模块的验收结论。其余历史版本及新候选不列为首批迁移必过项，由后续指定官方 APK URL 的任务逐个验证；现有规则不适用时再新增规则或策略，并走同一验收流程。QQ 9.3.70、9.3.75 不作为本轮强制交付条件。

旧 JSON 与旧支持证据作为历史资料保留；对已切换应用，不再作为运行时准入依据。尚未在新路径验收的版本标为新路径未验收，不自动写入新验收登记表或宣称已完成迁移，也不新增运行时 APK 白名单：这些版本仍可按正常区间与特征规则尝试匹配。新路径支持清单与旧模块历史支持记录明确区分。

### 有界回归集

对每个应用，按不可变 ruleId 的创建顺序取最近三条已完成验收的规则，每条选择首次成功验收记录中的一个精确 APK。该代表通过 recordId 固定；后来的官网回退或更低 versionCode 不自动更换代表。规则不足三条则全取。相同 APK SHA 去重，常规真实 APK 回归最多三个。

首次迁移时，新路径尚无已验收记录，允许在控制器明确的首次迁移任务中使用空历史回归集。报告必须注明“无历史回归样本”，不能记为历史回归通过；仍完整执行基准候选的身份核验、共享规则静态检查、适用单测、构建及独立运行验收。通过后由可信控制器生成首条登记记录，并固定该规则的首次验收代表。不得从旧 JSON 复制已验收状态来填补空集，也不得在本轮候选验收前把它当作已验收回归样本。

已有新路径验收记录时，登记表缺失、损坏、代表样本缺失或筛选异常导致的空集属于错误，不能自动切换为首次迁移模式。此判断以任务类型和可信登记快照为依据，不能只看本地文件是否为空。

常规集不额外并入各规则终点、最近三个版本或全部渠道变体。本轮候选单独检查，最多额外一份该应用 APK；已是代表样本则去重。更老规则的登记和支持状态不删除，但不声称本轮重新验证。

回归对同一个当前模块版本的共享解析代码断言：输入身份正确、期望规则及策略、整组唯一匹配、目标描述符与方法形状、无额外或缺失 Hook。若相邻规则产生冲突，即使某条规则单独能找到期望方法也算失败。

区间端点、空档两侧零/一/二匹配、任一侧歧义、策略冲突和缓存失效由小型确定性单测覆盖，不通过无限增加真实 APK 来覆盖组合。候选列表 mock 只测试决策器；真实 APK 检查必须执行共享 DexKit 查询。

## 流水线迁移

保持明确的 `app_id` 与应用策略输入，移除隐式微信默认值。保留下载校验、原始发现资料、APK/module 原字节、隔离适配环境和独立验收。

流水线提供两种明确的候选入口：自动发现官网 APK，以及手动指定 `app_id + apk_url`。指定 URL 时必须直接以该 APK 完成身份核验、现有规则检查、必要的适配、构建与独立运行验收，不能改用官网最新版，也不能因为版本较旧或已经登记就跳过所请求的适配与验收。URL 仍遵守该应用的官方源策略，不因手动指定而开放第三方来源；下载后核验真实包名、签名、ABI、versionCode 和内容哈希，不能根据文件名或 URL 推断身份。除最旧迁移基准外，其余历史版本由后续任务通过该入口按需验证或适配，不要求本轮批量执行，也不扩大以后每轮最多三个 APK 的常规回归集。

若指定 APK 暴露出需要修改历史区间的问题，仍按 `ROUTING_REVIEW_REQUIRED` 保留分析与提案，人工审阅具体路由后继续验收；指定 URL 不绕过历史路由约束。下载失败或身份不符时报告失败，不替换成另一 APK。自动发现路径仍可按已有有效证据去重；手动指定适配与验收请求必须实际执行检查和运行验收。

共用验证入口与适配控制器按以下顺序协作：

1. 共用候选准备逻辑取得 APK、核验真实身份并固定原字节；取得或构建待测模块，记录模块及源码身份。
2. 自动发现路径可以由外层控制器按完全对应的既有验收证据去重；手动指定 URL 的验证请求实际运行，验证核心不以“已有支持”拒绝未知构建或跳过验收。
3. 共用 checker 分别报告候选的正常路由/特征匹配结果与历史有界回归结果。两者通过后进入共用独立 ReDroid 验收；明确的首次迁移任务按空历史回归集约定继续，不要求先有适配 PR 或已有支持记录。历史回归失败或输入不完整时阻止验收通过及交付，不能因候选单独通过而放行。
4. 共用验证返回阶段结果、诊断及原始证据。只验证的调用到此结束，不自动分析、改代码、登记或更新 PR。
5. 允许适配的外层控制器仅在本轮候选缺失、歧义、冲突或确认的业务不兼容时，进入新增规则的适配分支，在隔离环境分析并提出新增规则、策略及暂定路由；满足向前条件时继续，不满足时报告 ROUTING_REVIEW_REQUIRED 并保留提案。候选模块构建后回到步骤 3，使用同一验证入口与断言，不另写“适配专用验收”。
6. 验收通过后，可信控制器独立核验 APK、模块、规则、commit 与证据，再生成登记或待审 PR。只有登记变化也可以形成记录 PR；PR 是输出，不是验证入口条件。保留人工合并控制。

历史回归失败与候选不兼容是不同结果。已有代表样本的规则、策略或目标断言失败时，停止候选交付并保留诊断，先定位公共解析器、路由、输入或基础设施的问题；不得进入只为新候选加规则的路径来掩盖失败，也不得删除失败样本、放宽断言或用本轮输出覆盖旧预期。修复后重跑失败阶段和受影响检查；若确需改变历史预期，必须保留旧证据并按新独立验收及人工审阅流程处理。环境 unavailable 同样不能转成规则不兼容或验收成功。

新增规则的首次验收使用提案内的暂定路由：先在隔离的候选源码中声明新规则和拟议区间，执行静态回归并构建候选模块，再让该模块按正常路由执行独立运行验收。暂定路由不直接进入正式分支或发布产物，也不通过测试专用强制选择绕过模块真实路由。验收通过后，登记实际规则、区间、源码提交及候选模块哈希，提交人工审阅；失败或 unavailable 时只保留诊断，不登记支持、不发布暂定路由。

候选区间的建立以验收前的登记快照为依据，不能把本轮候选自身先计入“最高已验收版本”。通过验收不自动改写暂定区间；若审阅后修改规则、区间或模块内容，先前证据不能直接证明修改后的模块通过，需重新执行受影响检查与独立运行验收。

已有 checkpoint/resume、PR 作者/head 校验、凭据隔离继续适用；record 步骤不再只负责把 `suggestedProfile` 升为 runtime-verified。过渡期间未迁移微信显式走 legacy 分支，不能触发隐式回退。

QQ 仍使用独立采集的自然请求 AppID 开关对照、scope/socket 归属和捕获完整性；微信/企微保留入口及二维码页开关对照。预期业务行为来自固定验收 contract 和核验过的 APK 事实，不能由待测规则自报成功。无账号验收不宣称真实登录、服务端接受或双设备共存。

运行验收区分实际失败与无法判断。设备、安装、框架或证据环境问题报告 unavailable；Hook 异常、应用崩溃、计划正确但行为错误需分析归因，不自动标为环境失败。取消、跳过、证据缺失和发布失败均不能写入成功状态。

## 测试迁移与交付门槛

| 层 | 保留部分 | 修改或新增部分 |
|---|---|---|
| core 单测 | 身份、结果模型等可复用约束 | 区间验证、空档选择、完整计划、策略冲突、回退及同版本构建禁止自动重划 |
| app 单测 | Hook 注册/回滚、QQ/Tinker bootstrap、回调行为 | 真实包版本/签名、策略显式绑定、有效代码及缓存 |
| checker | APK 身份校验、CLI、报告基础设施 | 调用共享 DexKit 查询，登记表预期断言 |
| APK 回归 | 校验下载/hash、按应用运行、异常汇总 | 最近三条规则首次验收代表选择，直接调用共享流程 |
| ReDroid | 环境、原始模块、自然请求/UI 断言和证据解析 | 新计划诊断、未知构建输入、无 PR 验收入口 |
| controller/Python | owner/head、安全和恢复约束 | 无代码改动的候选验收、登记发布、失败状态 |

实施顺序：固定依赖与 Linux JVM 探针 → 公共核心和共享查询入口 → QQ 解析/缓存/策略 → QQ 最旧迁移基准独立运行验收 → 企微最旧基准的规则/策略接入与验收 → 登记、回归和流水线切换。企微接入不应新增公共核心中的应用分支。

首批 QQ 查询可参考静态试验的 Context/枚举/字段/调用组合，但必须在最旧基准上重新验证。企微只接入最旧基准实际所需策略；近期 service 与 legacy local 的策略差异由应用层明确表达，后续指定 URL 需要另一策略时再新增，不以方法同时存在猜测策略。公共框架仍支持完整多 Hook 与显式策略绑定。具体初始区间及首次验收代表根据基准验收确定，不把静态试验样本自动标为支持。

交付必须证明：

1. 同一 Kotlin 规则与选择逻辑在 Linux checker 和 Android 模块执行；依赖版本一致，无 API 重复打包，native ABI 与页大小兼容实际目标环境。
2. QQ 9.3.1、企微 5.0.8 作为各自最旧迁移基准，在新路径通过独立静态及运行验收；其余版本留待后续指定 URL 验证或适配。旧支持证据保留，未迁移验收的版本不宣称新路径已支持；基准未通过时保留诊断，不完成该应用切换。
3. 装载器就绪后的 APK/split 解析和实际 Method 校验路径可用，业务 Hook 在自然请求前安装，已记录的代码输入或规则变化会使缓存失效；完整热补丁适配不作为本轮交付条件。
4. 企微显式选择 strategy，整组 Hook 原子安装；适配不靠名称猜行为。
5. 每应用常规 APK 集不超过三个，候选单列，断言来自独立验收登记。首次迁移无历史记录时仍完成候选验收并生成首条记录；已有登记后的异常空集不得冒充首次迁移。
6. 无规则改动的新版可以完成运行验收并登记；新增规则和封口不会改写历史查询/策略及其专用依赖的行为，公共逻辑调整经过回归。向前区间追加检查严格递增条件；回退、历史空档或同版本构建需要改规则时，明确停止自动路由更新并保留诊断。
7. 迁移应用的模块加载与 metadata 检查不再要求 `targets.json`；未迁移微信保持明确 legacy 路径。完成所有应用迁移后再删除全部旧加载/打包及测试路径。
8. 自动发现、指定官方 URL 与适配产物汇入同一候选输入；只验证不触发模型或写入支持，适配后回到同一验证核心。验收无 PR 前置条件，证据判定与登记/发布分离；每个迁移应用的重复和旧运行路径随切换删除。候选失败与历史回归失败分开报告；历史回归失败必须阻止交付，不能靠新增候选规则或改写预期放行。

README 在上述证据完成后再更新，只写用户能做的操作和实际支持效果。本文与登记 schema 是开发者材料。
