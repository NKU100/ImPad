# ImPad 常规静态回归代表与替补设计

## 目标与范围

常规 CI 每个 App 最多实际检查三个不同的历史行为组。微信、QQ 和企微使用同一套选样、替补和结果汇总逻辑。单 App 的适配或验证最多检查三个历史代表，当前候选另外执行精确静态检查和所需的运行时验收。模块构建串行检查三个 App，每轮最多检查九个历史代表。

早期实现用最近三条规则的首次验收 APK 做代表。迁移到语义验收后，常规回归逐条遍历迁移用例和全部 v2 验收记录。新设计恢复回归规模上限，并结束对一次性迁移数据的依赖。现行 v2 验收记录、APK 身份和归档证据全部保留。迁移样本先通过现行验收迁入候选池，旧证据由 Git 保存。[早期代表选择](https://github.com/NKU100/ImPad/blob/119daaa/scripts/ci/acceptance.py#L484) · [语义迁移提交](https://github.com/NKU100/ImPad/commit/d0bdc27)

## 先迁入历史样本，再退役旧数据

生产回归候选池统一读取各 App 的 `acceptance-v2.json`。切换前，把四个仅存在于旧表的样本作为一次性补验清单：

| App | 待补验版本 |
|---|---|
| 微信 | 8.0.69（3040）、8.0.79（3200） |
| QQ | 9.3.1（14378） |
| 企微 | 5.0.8（70675） |

旧表记录了这些版本的验收状态和原始 APK 哈希，但仓库当前没有旧记录所引用的完整静态、回归和运行报告文件。迁移目录里的 DEX 解析和反射证据可以用来检查静态预期。迁入 v2 时，先找回与旧记录整组 SHA-256 一致的 APK，再用当前模块跑共享静态检查及 ReDroid 验收，交给现有登记校验生成新的 v2 记录和归档。保留新记录与旧记录 ID 的对应关系作为一次性交接说明。这个过程用现有验收与登记能力完成，日常流水线只消费现行记录。

四个历史 APK 均通过独立 ReDroid 复验，各份有序 base/split SHA-256 均与旧记录一致。迁入后 v2 共有 12 条记录、10 份不同 APK。

迁入时常规窗口选中 5 个组。微信 3220、3200、3040 的原归档缺少机器可读的识别分支字段，按 APK 各成一组。QQ 的 17090、16920、16750、14378 合成一组。企微的 86692、84802、70675 合成一组。两款 App 的组内候选按上述顺序选择。

## 如何选代表

1. **加载并验证历史记录。** 只从现行 v2 验收表建立候选池。先校验整份验收表、归档绑定和同一组 APK 输入上的既有期望一致性。以 App ID 和有序的 APK 文件角色及 SHA-256 列表识别同一份样本，包含 base 和全部 split。对同一 APK 的重复验收，使用证据最完整、最近一次已验证的记录，记录 ID 用于最终排序。若同包记录的既有期望冲突，报告基线错误。
2. **根据可验证的行为证据分组。** 分组使用行为合同及版本、策略及版本、参与选中计划的识别器，以及 Hook 角色、阶段和真正影响行为的绑定形态。将这些特征编码成明确、有版本的结构。微信至少区分决策转发、缓存包装及缓存重读的已证明形态，以及声明类锁和字段锁。QQ 和企微同样使用已证明的识别分支、角色及绑定形态。类名、字段名、方法名、快照哈希、APK 哈希和版本号用于识别精确输入或排序。分组只使用这些名称体现出的结构关系，例如锁位于声明类还是字段。
3. **优先复用现有证据。** 先从 v2 已验证的静态报告和计划字段推导结构化特征。自由文本诊断只供排查。现有证据无法准确区分的分支，由识别器在后续报告中补明确字段。缺少证据的历史样本暂按独立组处理，等补齐证据再合组。落地前列出三应用现有样本的实际分组，逐项检查合并依据。
4. **确定常规窗口。** 每组按 `versionCode` 从高到低排列不同 APK。相同构建号时按验收时间排序，再以记录 ID 打破平局。每组首选排序最前的 APK。若组数超过三个，按各组首选排序保留前三组，稳定的组标识用于最终打破平局。摘要列出未入选的组。组数不足三个时，按实际组数执行。

版本号直接排序容易把多个名额花在同一行为上。单独使用 `strategyId` 会把不同绑定折叠到一起。例如历史上的微信 `3040`、`3200`、`3220` 共用一个策略，但 `3220` 的锁来自独立字段。这个差异用于说明分组粒度。生产候选以现行验收表为准。企微 `84802` 和 `86692` 的现存报告支持同组判断，最终以全部结构化特征核对为准。

## 同组替补与下载限时

选出的每个组先查缓存。按组内排序检查可用缓存，验证 base、split 及对应记录要求的完整哈希。只要有正确的缓存包，就用排序最高的缓存样本。缓存不可用时，按组内顺序下载候选，直到取得正确原包或组内候选用尽。完整包的哈希和记录不一致时，弃用下载到的文件，继续尝试同组下一份。组之间各自独立。相同 APK 不因重复验收记录而重复尝试。

替补适用于现有下载器能识别的原包不可用情况，包括有明确 HTTP、网络错误或下载文件摘要不符的情况。取得正确包后，用**该包自己的验收记录**校验完整静态预期。检查器执行失败、发现规则回归、基线或归档证据无效时，仍按现行规则处理失败。每组取得第一个正确包后，就执行一次静态检查并记录结果。

沿用现有网络行为。通用 HEAD 超时 30 秒，GET 网络操作超时 120 秒，QQ 专用 CDN 回退沿用现有重试次数、探测和正文传输预算。每组和每 App 不新增下载时间或候选次数上限。120 秒是网络操作超时，持续有进度的传输可以超过两分钟。QQ #157 的两次有效下载耗时 3 分 09 秒和 3 分 33 秒。单次静态检查的 5 分钟上限和 ReDroid job 的 25 分钟上限沿用现有配置。[QQ #157](https://github.com/NKU100/ImPad/actions/runs/45918106689) · [下载实现](../../../scripts/ci/fetch_latest_wechat_apk.py) · [运行时工作流](../../../.github/workflows/runtime-validation.yml)

因此，三个组的上限只约束实际静态检查次数。网络最坏耗时仍取决于组内候选数量和现有下载器行为。

## 验收表与回归报告的版本

继续使用 `acceptance-v2.json`。现有记录已包含 APK 输入哈希、完整计划和静态识别证据。第一版分组用可验证的字段推导，包含选中计划的识别器、合同与策略修订号、Hook 角色及阶段，以及经过归一化的关键绑定。分组算法独立版本化。同一批验收记录在相同算法版本下，应产生相同的组和候选顺序。

如果识别分支只能从诊断文本猜测，缺少证据的历史样本暂按独立组处理。需要明确区分的分支，由识别器提供稳定的结构化字段，随新的静态报告归档。已有 v2 验收记录及归档的字节保持原样。

新的回归报告使用独立的 schema 版本，记录分组算法版本、验收快照、各组候选顺序、替补尝试及实际受测记录。新登记让 v2 记录的归档引用绑定这份报告。退役迁移目录时，v2 读取器解除对旧目录的依赖，新记录直接绑定现行 v2 快照与分组证据。既有记录的迁移引用保留为历史元数据。

## 验收证据与徽章

- 运行开始时，把分组算法版本、验收快照和选中的组及其候选顺序固定到回归基线。模块构建、候选适配、独立运行验收、正式登记及验收复用使用同一份选择依据。选择过程与本次缓存状态和网络结果无关。
- 每组写一条结果，包含组标识、候选记录 ID、使用的记录、替补尝试及结果。通过时保留实际受测样本的静态证据和哈希。全部候选均取不到时，记录该组跳过及每个候选的失败原因。运行结果只记录必要原因和哈希，继续按现行规则处理可能含访问令牌的 URL。
- 验收复核从固定快照重建分组和窗口，验证受测记录确属该组、每个入选组有且仅有一条结果，以及跳过组的候选均已尝试。登记记录保留本轮分组与实际覆盖证据。既有 v2 记录和归档保持原样。旧记录中的迁移引用作为历史元数据保留，生产读取和复用依赖现行记录身份、归档哈希和验证实现指纹。新登记保存新的分组证据，复核须验证当前分组方案。
- 窗口内各组均有样本通过时，构建徽章显示「通过」。组内成功替换样本也算覆盖。窗口内有组因原包均不可用而跳过、其他构建条件通过时，显示「通过（有回归跳过）」。适配徽章同样反映所选组覆盖情况。窗口外样本及组列在摘要里，属于常规选择范围之外。真实检查失败仍优先显示失败。

## 实现落点与验收

把选择逻辑放在共享语义回归基线中。下载和检查沿用现有静态回归入口。同步更新适配控制器及验收校验中目前要求逐条覆盖全部记录的约束。特别要让适配准备阶段只暂存当前候选和入选组实际选到的代表，避免在静态回归开始前先下载全部历史 APK。显式全量复查可单独检查现行验收表中的所有不同 APK，常规 CI 仍按选出的窗口执行。

实现验收至少覆盖：

- 对四个旧样本核对旧记录 ID、整组 APK 哈希和补验结果。已迁入的样本可用同一选择器参选，无法迁入的样本有明确的交接记录。同一组完整 APK 输入重复入库只占一个样本，同策略下确有不同绑定形态的样本能进入不同组。
- 从生产工作树移除旧表、迁移目录和专用投影后，候选发现、单 App 适配、正式登记、验收复用、常规模块构建均可按现行表运行。已发布的 v2 记录和归档字节保持一致。
- 增加第四个行为组后，常规选择仍稳定在三个。新增同组记录只会更新组内排序，原验收记录仍完整保留。
- 三应用分别验证首选不可用后同组替补通过、所有候选不可用后标记跳过，以及取得正确包后规则回归失败的路径。验证首选下载超过两分钟但仍正常传输时继续使用现有下载行为。
- 替补和备注能随运行结果进入登记归档。变造组、替换不属于该组的验收记录、遗漏应尝试的候选，或用旧报告冒充当前结果时，复核拒绝。
- GitHub Actions 验证常规模块构建和单 App 的完整验收入口。核对实际检查数量、APK 哈希、跳过原因、归档内容和最终徽章。
